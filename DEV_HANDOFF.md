# Шпаргалка для разговора с разработчиками

Короткое объяснение по каждой фиче — как это реализуется относительно
Prodigy, что реально нужно менять (фронт/бэк), и на что отвечать, если
скажут «Prodigy не даст». Не техническое задание, а разговорник.

## Общая мысль, с которой стоит начать

Из четырёх идей, которые обсуждались, три полностью убраны из скоупа
(«Найти и заменить», «Частые ошибки», таймер усталости глаз и ещё пара
мелочей) — то есть список того, что реально нужно, короче, а не длиннее,
чем был. Это стоит сказать вслух в начале встречи.

## 1. Буфер слов, сохраняется по проекту

**Если скажут:** «нужна новая таблица в БД и API» — **это не так**.

Prodigy-рецепт поддерживает конфиг-поле `"javascript"` — произвольный JS,
который подключается на каждой странице разметки. Этот JS может читать и
писать `localStorage` прямо в браузере — без бэкенда, без БД, без
изменения схемы. Это добавление в конфиг рецепта, не новая фича бэкенда.

**Оценка:** тривиально, часы, не дни.

## 2. Точная настройка плеера (ползунки 1%, общий/для клипа, повтор в 3 состояния)

**Если скажут:** «аудио-виджет — встроенный Svelte-компонент Prodigy, мы
не можем его трогать» — верно только частично.

Исходники Svelte недоступны, но `"javascript"`-хук в конфиге рецепта
выполняется после отрисовки каждого примера — можно взять DOM-узел,
который Prodigy уже создал (обычный `<audio>` внутри), через
`document.querySelector`, и либо подменить окружающие его контролы своими,
либо просто управлять тем же `<audio>` его стандартным JS API
(`.volume`, `.playbackRate`, `.loop`, `.currentTime`). Сам Prodigy этот
`<audio>`-элемент никуда не убирает — им можно управлять программно, не
трогая закрытый Svelte-код. Это стандартный приём при «headless»
использовании Prodigy, а не хак.

**Оценка:** небольшая-средняя, но только фронтенд — бэкенд и БД не
трогаются.

## 3. Аналитика WER/CER (дашборд, по проектам, по дням, настраиваемые блоки)

**Если скажут:** «в Prodigy нет менеджерского дашборда, это отдельная
большая фича» — по факту UI действительно нет, но данные уже есть.

Ассессоры уже видят WER/CER по каждому сотруднику — значит, где-то уже
есть пайплайн подсчёта. Дашборду нужен небольшой **read-only** Python-
сервис, который берёт эти уже существующие данные, группирует по
проекту и дате, и отдаёт JSON. Сам дашборд — статичная фронтенд-страница
(этот HTML-прототип — фактически готовый визуальный спек для неё). Этот
сервис не трогает процесс разметки, лицензию Prodigy или существующие
рецепты — это отдельный, чисто добавочный путь чтения данных.

**Фаза 1** (уже согласовано в переписке): только блоки WER/CER, остальные
метрики (F1 и т.д.) — отдельным разговором позже. Это сознательно узкий
скоуп.

**Оценка:** средняя — основная работа это агрегирующий запрос + маленький
API (порядка 1-2 дней), фронтенд уже спроектирован в прототипе.

## 4. Настраиваемые/перетаскиваемые блоки дашборда

**Если скажут:** «хранить кастомную раскладку под каждого менеджера —
нужна таблица настроек пользователя» — для версии 1 не нужна.

Раскладка и видимость блоков хранятся в `localStorage` браузера — тем же
способом, что и буфер слов. Если позже понадобится, чтобы раскладка
следовала за менеджером между устройствами — это отдельное, явно
осознанное расширение на будущее, не требование для v1.

**Оценка:** тривиально для v1 (только браузер).

## 5. Логин / QR

Уже реализовано и работает в проде (см. текущий сайт) — в прототипе
показано только для целостности картинки, доработок не требует.

## 6. Убранные фичи

«Найти и заменить», «Частые ошибки», таймер усталости глаз, переходы по
сегментам, «База КЗ», «Инспектор правил», редактирование истории — по
всем этим пунктам работы для разработчиков **не прибавляется, а
убавляется**: это то, что не нужно реализовывать.

## 7. Горячие клавиши

Обычный ребайнд обработчика в том же `javascript`-хуке рецепта, который
уже сегодня биндит клавиши — замена Alt+1-9 на Ctrl+Shift+1-9.

## Вывод

Пять из семи пунктов — это чистый фронтенд/браузер (часы работы, не
дни), не требуют трогать бэкенд, БД или лицензию Prodigy. Только
дашборд аналитики (п.3) требует одного маленького нового read-only
сервиса — и даже он не касается самого процесса разметки. Это разумный
объём работы, не «переписать всё с нуля».
